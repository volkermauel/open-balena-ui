# Design: OS image downloader with fleet provisioning

## Context

- balenaCloud serves the public OS catalog that powers https://www.balena.io/os:
  - Versions:
    `GET {BALENACLOUD_API_URL}/v7/release?$select=raw_version&$filter=(is_final eq true) and (is_invalidated eq false) and (status eq 'success') and (semver_major gt 0) and (belongs_to__application/any(bta:(bta/is_host eq true) and (bta/is_for__device_type/any(dt:dt/slug eq '<slug>'))))&$orderby=semver_major desc,semver_minor desc,semver_patch desc,revision desc`
    — no auth required.
  - Image bytes:
    `GET {BALENACLOUD_API_URL}/download?deviceType=<slug>&version=<raw_version>&fileType=.img[&developmentMode=true]` —
    streams the uncompressed image; `developmentMode=true` selects the development image variant.
- openBalena instances do not implement `/download` (verified 404) — image bytes must come from balenaCloud.
- openBalena implements `POST {REACT_APP_OPEN_BALENA_API_URL}/download-config` (verified present). It builds the fleet
  `config.json` and accepts the UI user's JWT (Bearer) — the same JWT the UI server already verifies with
  `OPEN_BALENA_JWT_SECRET`.
- Config injection (what `balena os configure` does): write `config.json` into the image's boot partition.
  Implementations exist as npm packages: `balena-config-json` (`getBootPartition`, read/write) on top of
  `balena-image-fs` + `file-disk` + `partitioninfo`.

## Goals

- One click from a fleet to a compressed, pre-provisioned OS image.
- balenaCloud is touched at most once per (device type, version, variant).
- Identical fleet configurations reuse cached compressed artifacts.
- Bounded disk usage.

## Decisions

### D1: Server-side proxy, not browser-direct

The browser never talks to balenaCloud: no CORS/egress problems per deployment, a single egress point, and it enables
server-side caching. `BALENACLOUD_API_URL` (default `https://api.balena-cloud.com`) is server-env configurable for
air-gapped mirrors.

### D2: Two cache tiers, LRU-evicted, size-capped

Cache dir (`OS_IMAGE_CACHE_DIR`, default `./os-image-cache`):

```
img/   pristine: {deviceType}__{version}__{prod|dev}.img      (downloaded at most once)
out/   artifacts: {deviceType}__{version}__{prod|dev}__{configSha16}.{zip|gz}
tmp/   in-flight scratch files, cleaned on job end/failure
```

- Pristine download dedup: an in-process lock map per cache key; concurrent prepares for the same key await the first
  download (balenaCloud "touched once").
- Artifacts are keyed by a SHA-256 (first 16 hex chars) over the canonicalized config JSON + format, so identical
  settings reuse the artifact.
- LRU (by file atime/mtime, tracked in an index) across both tiers; total bytes capped at `OS_IMAGE_CACHE_MAX_GB`
  (default 20). Eviction runs after each new file lands; files belonging to a running job are never evicted.

### D3: Job model (prepare is long-running)

`POST /os-images/prepare` returns `{ jobId }` immediately; work happens async:

phases: `downloading` (with byte progress when Content-Length is known) → `injecting` → `compressing` → `ready` (or
`error` with message). Job registry is in-memory (`Map<jobId, JobState>`), IDs are `crypto.randomUUID()`.
`GET /os-images/jobs/:id` polls status; `GET /os-images/jobs/:id/download` streams the artifact with
`Content-Disposition: attachment; filename="<deviceType>-<version>[-dev]-<fleetSlug>.<ext>"`. All three behind
`authorize` + `dosProtect`.

### D4: Config generated by openBalena with the user's own JWT

The server forwards the caller's `Authorization: Bearer <jwt>` to `POST {REACT_APP_OPEN_BALENA_API_URL}/download-config`
with `{ appId, version, network, appUpdatePollInterval, developmentMode, wifiSsid, wifiKey }`. No server-side service
account; the config is generated with exactly the permissions of the logged-in user. Errors (401/400) are surfaced to
the dialog.

### D5: Compress after injection; offer `.zip` and `.gz`

Injection needs the uncompressed `.img`, so the pipeline is: pristine `.img` → copy → inject → compress (`.gz` via
`node:zlib` gzip stream; `.zip` via `archiver`) → artifact. The pristine tier stays uncompressed (needed for future
injections).

### D6: Cache status drives UI badges

`GET /os-images/cache-status?deviceType=<slug>` returns the cached version set per variant and artifact availability.
The wizard's version dropdown marks entries with a "cached" chip when either the pristine image or any configured
artifact for that (version, variant) exists.

## Risks / Trade-offs

- **Native modules through `ncc`**: `balena-image-fs` pulls `ext2fs` (native `.node`). The server build is
  `ncc build server/index.ts -m`. ncc emits native modules as assets — this must be verified (`npm run build:server`,
  then start `dist/server/index.js` and run a prepare against a small image). If assets break, fall back to `--external`
  for the native chain and ensure the Docker runtime stage keeps the required `node_modules`.
- **Development images availability**: not every device type/version has a dev build (balenaCloud 404). The dialog must
  surface the error cleanly.
- **Disk pressure**: capped by LRU; defaults are conservative. Cache dir should be added to `.gitignore` and documented.
- **Memory**: all transfers are streams (fetch body → fs stream; fs stream → HTTP response); no full-image buffering.
- **Job registry is in-memory**: acceptable for a single-instance UI server; jobs do not survive restarts (documented).

## Migration Plan

Purely additive: new routes, new deps, new env vars with defaults. No changes to existing routes/resources.

## Open Questions

- None blocking. (Artifact retention across server restarts is covered by the on-disk cache; only in-flight jobs are
  lost.)
